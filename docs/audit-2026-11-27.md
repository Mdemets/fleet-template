# Fleet audit, 2026-11-27 - faults by design and in operation

Scope: the pull-based queue at D:/fleet, the worker and reaper scripts, the three nodes.

## Operational faults, live now

### O1 - CRITICAL: node-c cannot authenticate; the fleet runs on one worker

worker.log on DESKTOP, every ~36 seconds since 09:42Z:

    2026-11-27T09:42:46Z  loop error: System error 86 has occurred.    (invalid password)
    2026-11-27T09:43:59Z  loop error: System error 1909 has occurred.   (account locked out)
    ... repeating, latest 09:47:36Z

verify-worker-share.ps1 on DESKTOP fails with 1909; the same check on node-b passes. Lockout policy
is 10 attempts with a 10 minute duration, so the worker's retry loop keeps the account locked: even
a correct password cannot get in now.

Consequence: half the fleet is dark and nothing on the coordinator shows it. The queue is empty, the
reaper logs retried=0 done=0 dead=0, and everything looks healthy.

Suspected cause: the 09:55 credential rotation left a stale value in DESKTOP's coordinator.cred. The
exact failure is unproven; what is proven is that the stored credential does not work and that the
retry loop turned one bad password into a lockout.

### O2 - MEDIUM: node-b's worker is idle, not proven healthy

No errors, but worker.log has not been written since 2026-11-26T13:06Z. The loop reconnects only
when Test-Path fails, so a half-open SMB session would keep it quiet while unable to work. Silence
is not evidence of health.

## Design faults

### D1 - CRITICAL: the reaper measures the task's age, not the claim's

Invoke-FleetReaper.ps1 line 55 computes age from the claim file's LastWriteTime. Move-Item within
the share preserves that timestamp - measured: a file backdated three hours and moved kept its
LastWriteTime, so the reaper saw 10,800s of age on a claim made seconds earlier.

Effect: any task that waited in the queue longer than timeoutSeconds + 300 is judged stale the
instant it is claimed and is requeued while the worker is still running it. Duplicate execution,
silently. The longer the backlog, the worse it gets.

### D2 - HIGH: one bad credential becomes a lockout, with no backoff and no alert

The worker retries every 30s on error with no backoff and no lockout awareness. Against a 10/10min
policy that turns one stale credential into a locked account in about six minutes, and the retries
then hold it locked. Nothing notifies the coordinator; the only trace is a local log.

### D3 - HIGH: a hung worker looks identical to a healthy one

The worker is an endless loop, so the scheduled task reports Running forever and LastTaskResult
never reflects health. Both nodes report Running right now; one of them is dead.

### D4 - HIGH: timeout kills the wrapper, not the work

Process.Kill() terminates the PowerShell that ran the task; its children survive. A timed-out task
keeps running while the reaper requeues it - duplicate work with two live processes.

### D5 - HIGH: the share password is passed on a command line

net use with the plaintext password places it in the process command line, readable by
administrators and by tooling that can query process arguments.

### D6 - MEDIUM: the stored credential is protected by the machine, not the user

DPAPI LocalMachine scope: any local principal on the worker can decrypt coordinator.cred.

### D7 - MEDIUM: output is truncated silently

stdout and stderr are cut at 8000 characters with no flag in the result, so a consumer cannot tell
a short output from a truncated one.

### D8 - MEDIUM: the result id can never match the claim

The worker derives the id from the file base name, which is task-<id>, not <id>. If a task JSON
omits id, the result is written as result-task-<id>.json, which the reaper can never match to the
claim: it requeues and the task runs again.

### D9 - LOW: kind is decorative

Every payload is executed as PowerShell regardless of task.kind.

### D10 - LOW: nothing is ever pruned

done, dead, results and the logs grow without bound.

### D11 - LOW: pinned queues can starve the shared pool

The one-task-per-sweep limit counts pinned tasks too, and pinned queues drain fully, so a busy
pinned queue blocks shared work for the whole sweep.

### D12 - LOW: JSON is written with a BOM

Set-Content -Encoding UTF8 on PowerShell 5.1 emits a BOM; PowerShell tolerates it, other JSON
consumers may not.

## Verified sound

- Claim by move is atomic on the share: a pinned task cannot be taken by another node.
- worker.lock prevents a second worker on the same node.
- Results are written to a .tmp name then moved, so a reader never sees a partial result.
- Requeue is capped at 3 attempts and then parked in dead.

## Correction to an earlier audit statement

The coordinator README previously said audit.jsonl has no producer. That was wrong.
FleetWorker.ps1 appends to results/<node>/audit.jsonl on every finished task. The file is absent
only because no task has finished since results was cleared. The README has been corrected; the
claim should not have been made without reading the worker.

## O1 resolution and root cause (10:54Z)

Recovered. The stored credential was correct; the **running worker held the old password in memory**, because the worker reads coordinator.cred once at startup. Rekeying the file left the process authenticating with a dead password, which retried every 36s and locked the account.

Two lessons:

1. Rotating the credential requires stopping the task **and killing the process**. Replacing the file is not enough, and verification from a fresh session will pass while the worker is still broken.
2. The worker has both an at-startup trigger and a 5-minute repeating trigger with stop-if-still-running disabled, so instances stack. Only the worker.lock file prevents duplicate work; nothing prevents duplicate processes.
